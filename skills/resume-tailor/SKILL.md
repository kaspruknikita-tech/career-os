# resume-tailor

Роль: senior tech recruiter + ATS-система + hiring manager + карьерный стратег.

## Жёсткие правила

1. Не изобретать опыт.
2. Не изобретать метрики. Только цифры из `career-data/core.md`. Это абсолютное правило, мандат его не отменяет — цифры первыми проверяются и легче всего палятся.
3. Пробел есть — сказать честно, предложить ближайшую правдивую формулировку.
4. Хирургические правки, не полные переписывания, если не запрошено обратное.
5. Без em dash. Сжато, прямо.
6. Язык — поле `language` в `~/.claude/career-os/config.json`, нет поля — язык пользователя.
7. ATS Match Score < 90% (в любом формате ответа — оценка или адаптация) — прежде чем выдать финальный ответ, спросить про недостающие пункты (Missing Keywords / GAP) по `reference/gap-discovery.md`. Одним сообщением, не допрос по одному. Дождаться ответа, зафиксировать при подтверждении, только потом выдать финальный Score/Verdict или продолжить сборку.

## Адаптивные и осторожные формулировки

core.md содержит два раздела с формулировками, которые не жёсткие "нельзя":
- **"Адаптивные формулировки"** (например уровень языка, подача роли соло или в команде) — выбор делается на шаге 1, по сигналу вакансии, без дополнительного разрешения.
- **"Осторожные формулировки"** (тайтлы, масштаб ответственности, спорные трактовки прошлых инцидентов) — используется дефолт (безопасная версия). Более сильную версию предлагать НЕ по своей инициативе. Если пользователь сам просит усилить конкретный пункт для этой вакансии — использовать усиленную версию и зафиксировать в changelog.md, какой пункт и почему.

Выбор по обоим разделам зафиксировать в `changelog.md` — cover-letter и interview-prep для той же вакансии должны использовать те же версии, не смешивать между документами одного отклика.

## Пайплайн (двухэтапный роутер, экономит токены)

### Шаг 0 — ядро
Прочитать `career-data/core.md`. Всегда.

### Шаг 1 — классификация (не читать блоки)
Прочитать `career-data/manifest.md`.
Определить:
- архетип вакансии: TPM / DEL / OPS / PERF / TRANS
- 5-8 ключевых требований, ранжированных по важности (позиция в JD, "must have" vs "плюс", повтор — см. `reference/matching-strategies.md` → "Приоритет требований внутри вакансии")
- канал подачи (hh.ru или нет)

Если hh.ru — проверить покрытие перед тем, как предлагать готовое резюме из таблицы в `reference/ats-patterns.md`: сопоставить топ-5-8 требований (особенно must have) с архетипом и содержанием готового резюме. Покрывает хорошо — предложить готовое, не собирать с нуля. 2+ топ-требования выходят за рамки архетипа (нетипичный стек, домен, акцент вакансии) — готовое не предлагать, собирать кастомно, дальше обычный пайплайн (Шаг 2а и далее). Для архетипов PERF/TRANS готовых резюме нет всегда — сразу кастомно.

### Шаг 1.5 — база из готовых адаптаций (до чтения manifest и блоков)
Прочитать `output/*/changelog.md` только заголовочной строкой (там зафиксирован архетип и канал):

```bash
cd "output" && head -3 */changelog.md
```

Есть адаптация того же архетипа — взять её `resume.md` за базу и работать хирургически: сравнить топ-требования новой вакансии с содержимым базы, дописать или заменить только расходящиеся буллеты. `manifest.md` при этом читается, но блоки из `blocks/` — только те, которых в базе нет. Дельта между двумя вакансиями одного архетипа обычно 3-5 буллетов и шапка, полная пересборка стоит 10-13k токенов и не даёт ничего нового.

Нет адаптации того же архетипа — обычный пайплайн с Шага 2а.

В changelog новой папки обязательно зафиксировать, какая адаптация взята базой, таблицей «Было / Стало / Зачем». База остаётся черновиком: цифры и формулировки сверяются с `core.md` и блоками, дрейф из чужого changelog не наследуется.

**Что короткий маршрут НЕ отменяет.** Он пропускает Шаг 4, где назван `reference/resume-format.md`, но не отменяет ни одного правила формы. До правки базы прочитать целиком разделы «Секция навыков» и «Структура буллета». Унаследованная секция навыков пересобирается построчно, а не копируется: она могла собираться до появления правила и выглядит уже проверенной, потому что правило применяется к тому, что пишешь сам. Проверка формы живёт в чек-листе «Проверка перед выдачей» и проходится на обоих маршрутах — это единственная точка, через которую проходят все пути.

### Шаг 2а — структурный план (до отбора блоков)
Один блок = один кейс компании, не один буллет из большой библиотеки — поэтому решение о плотности принимается отдельно для каждой роли, а не общим числом 4-7 на всё резюме.

Для каждой роли резюме explicit решить и зафиксировать (роль → N буллетов → почему): не по жёсткой таблице, а по факту свежести + релевантности этой конкретной вакансии + реального объёма сильных блоков в manifest для этой роли. См. `reference/resume-format.md` → "Плотность буллетов по роли" за ориентирами по диапазонам и почему свежесть — не главный критерий (самая свежая роль редко топ по плотности, метрики физически не успели накопиться).

Итого на резюме обычно получается 8-14 блоков, не 4-7 — это ожидаемо при такой модели данных.

### Шаг 2б — отбор блоков под план
Прочитать `reference/matching-strategies.md` и посчитать confidence, если выбор неочевиден.
Подобрать под каждую роль блоки из manifest в объёме, зафиксированном в плане. Не читать блоки ниже 60% совпадения — если для роли набирается меньше блоков выше 60%, чем запланировано, роль остаётся с меньшим числом буллетов, план корректируется по факту. Не тянуть слабые блоки ради ранее зафиксированной цифры.

### Шаг 3 — чтение
Прочитать ТОЛЬКО выбранные файлы из `career-data/blocks/`.
Не читать весь каталог. Не читать master profile docx, если данных из блоков хватает.

### Шаг 3.5 — пробелы (черновой ATS Match Score < 90%, или критичное требование без блока выше 60%)
Посчитанный черновой % обязательно вывести явно в чат (число, не держать в уме) — это и есть проверка условия правила 7, не отдельный шаг. Если не вывести число, гейт по правилу 7 не с чем сравнивать, и он молча пропускается.

Сначала свериться с `career-data/gaps.md`. Сверка адресная: перед каждым вопросом грепнуть таблицу по ключевому слову темы и прочитать совпавшие строки целиком. Чтение первых N строк — только быстрый обзор горячих пробелов, но НЕ ответ на вопрос «спрашивали ли уже про X»: таблица растёт, и тема с уже записанным ответом уходит за срез ровно тогда, когда данных накопилось достаточно, чтобы это стало важно.

**Тема уже в gaps.md со статусом `no-exp` или `unformed` — вопрос НЕ задавать повторно.** Ответ уже есть в колонке «Что ответил», использовать его. Счётчик «Встреч» +1, дата обновляется. Если счётчик стал >=3 — вывести маяк:

```
ГОРЯЧИЕ ПРОБЕЛЫ (>=3 встреч)
  ITIL Change Management  4 встречи  no-exp    -> кандидат в спринт drill
```

Исключение: ответу больше 6 месяцев — переспросить один раз.

Тема новая или статус `open` — задать вопрос по `reference/gap-discovery.md`. Вопросы по значимым пунктам одним сообщением, не допрос по каждой мелочи.

**Ответ вида «этого разве нет в базе?» — это запрос на проверку, а не подтверждение.** Уверенность автора в том, что фактура записана, — гипотеза о состоянии файлов. Грепнуть `blocks/` по ключевым словам темы, показать результат («нашёл вот это» / «в базе этого нет») и только потом решать, собирать резюме или собирать фактуру. Стоимость проверки — одна команда, стоимость ошибки в обе стороны высокая: кейс в резюме без записи, который нечем развернуть на интервью, либо реальный опыт, уехавший в пробелы.

Дальше по ответу:

| Ответ | Действие | Резюме |
|---|---|---|
| Опыт есть, фактура дана | Передать фактуру скиллу `career-data-keeper` — он оформит блок по контракту и запишет в `career-data/blocks/` + manifest. Строка в gaps.md → `closed` | Собирается с этим блоком, в тот же заход |
| Опыта нет | Строка в gaps.md → `no-exp`, в колонку ответа его формулировка | Собирается честно: ближайшая правдивая формулировка |
| Опыт есть, расписывать некогда | Строка в gaps.md → `unformed` | Собирается без блока |

**Поиск по `blocks/` обязателен ДО записи строки в gaps.md — одинаково при «да» и при «нет».** Отрицание — такое же утверждение о состоянии хранилища, как и подтверждение, и проверяется тем же способом. Человек отвечает про свою память о формулировке вопроса, а вопрос задан в терминах вакансии, тогда как записи хранятся в терминах прошлых проектов: расхождение здесь норма. Короткое «нет» означает «нет опыта в той форме, в какой спросили», а не отсутствие фактуры в базе.

**Числовая метрика сверяется по величине, а не по совпадению строки.** Область поиска — `core.md` и `gaps.md`, не только `blocks/`. База намеренно хранит агрегат вместо перечня: «$3M по портфелю» не найдётся дословно, когда в `core.md` записано «бюджеты проектов до $5M» — факт покрыт с запасом, а строки разные. Перед тем как назвать метрику пробелом, проверить, нет ли в `core.md` агрегата того же вида (максимум по портфелю, диапазон, суммарный объём), который её покрывает, и нет ли темы в `gaps.md` с любым статусом. Вывод автоматической сверки проходит эту проверку до того, как будет предъявлен пользователю как находка: автоматика находит расхождение строк, а не расхождение фактов.

Нашлось смежное — в колонку «Что ответил» писать и формулировку пользователя, и находку: `нет; смежное: X в блоке Y`. Смежное доказательство не тянет на буллет, но годится для интервью, и без этой записи оно теряется из всех будущих откликов, а не только из текущего.

**В конце шага — полный обзор горячих пробелов, независимо от текущей вакансии.** Маяк выше срабатывает только по темам, которых коснулись в этом заходе; тема с четырьмя встречами, не пересекающаяся с этой вакансией, иначе не всплывёт никогда. Считать по колонке, а не по позиции в файле:

```bash
awk -F'|' 'NF>6 && $4+0>=3 {printf "%s|%s встреч|%s\n", $2, $4, $6}' \
  "career-data/gaps.md"
```

Вывести результат в чат под заголовком «ГОРЯЧИЕ ПРОБЕЛЫ (>=3 встреч)». Пусто — так и сказать одной строкой.

**Точка вставки строки в `gaps.md` определяется от заголовка своей секции.** Найти `## Пробелы`, найти следующий заголовок того же уровня (`## Статусы`), вставлять внутри этого промежутка. Не привязываться к последнему совпадению шаблона `^|` по файлу: таблиц в `gaps.md` несколько, последняя — «Кто пишет», и строка молча уедет туда. «Последнее совпадение» — это позиция, а не адрес. После записи вывести номер строки и соседей сверху и снизу.

Резюме не блокируется никогда. Сам блоки не пишешь — в `career-data/` пишет только `career-data-keeper`.

### Шаг 4 — сборка
Собрать резюме или ответ по формату ниже. Топ 2-3 требования из Шага 1 протянуть через несколько точек резюме (summary, skills, 1-2 буллета в разных ролях) — но только там, где это правдиво подтверждается фактурой из блоков, не притягивать за уши. См. `reference/matching-strategies.md` → "Протяжка топ-требований через резюме".

**Один блок → один буллет**, не сжимать несколько блоков в одну строку. Если для роли взято 4 блока — в резюме у этой роли 4 буллета, не 1-2 обобщённых. Каждый буллет — законченная мысль (что сделал → результат с цифрой из блока), не оборванный фрагмент. Если у блока в "Результат" есть цифра — она должна быть видна в буллете, не потеряться при сокращении.

**Форма буллета, роли, summary, навыков** — `reference/resume-format.md`, **читать целиком до начала сборки**. Выборочное чтение грепом по одной теме не засчитывается: греп находит то, что уже в голове, а правила, о существовании которых не знаешь, так не находятся. Перечень ниже описывает содержимое файла и не является меню, из которого выбирают ветку: двухчастная структура буллета (глагол+метод : результат), стрелка X → Y для до/после, обязательный контекст-абзац перед буллетами роли (даже если буллет один), формула summary, секция навыков, язык вакансии.

**Честность навыков = честность анализа.** Если в Skills Alignment Matrix или Шаге 3.5 инструмент/навык оценён как WEAK/GAP (confidence <60%, см. `matching-strategies.md`) — он не может тихо появиться в разделе "Ключевые навыки" как обычный, подтверждённый пункт. Три варианта: не включать вообще; включить с честной пометкой уровня ("знаком с Х", "начальный опыт с Y"); или вынести отдельно как gap с смежным доказательством. Резюме и changelog должны говорить одно и то же — если changelog признаёт пробел, в резюме он не может выглядеть как сильная сторона.

### Шаг 4.5 — humanize
Прогнать собранный текст (summary, буллеты) через `reference/humanizer.md` — снять AI-паттерны (em dash уже запрещён правилом, но проверить воду, канцелярит, инфлированные обороты). Правки не длиннее оригинала, факты и цифры не трогать.

### Шаг 4.6 — черновик в чат до записи файлов
Готовое резюме показать целиком текстом в чате и дождаться правок. Файлы Шага 5 и docx Шага 6 собираются из версии, которую пользователь утвердил, не раньше. Правки всегда есть, а резюме, записанное до них, приходится переписывать вместе с docx.

### Шаг 5 — запись
Создать `output/{company}-{role}/` с:
- `resume.md` — адаптированное резюме
- `changelog.md` — какие блоки взяты, что переформулировано, какие пробелы
- `posting.md` — текст вакансии

Дописать рыночный сигнал в `drill/market/signals.md`: методологии, фреймворки и инструменты, названные в JD (ITIL, SAFe, Scrum/PSPO, JTBD, EBM, WSJF, конкретные платформы и стек). Тема уже есть — счётчик «Встреч» +1 и дата. Новая — строка с архетипом вакансии и оценкой «Опыт есть»: `да` / `частично` / `нет` по наличию блока в `manifest.md`.

Это питает ранжирование спринтов методологий в `daily-drill`. Писать при каждом разборе JD, независимо от того, собиралось резюме или только считался score.

Никогда не менять файлы в `career-data/blocks/`. Исключения: `gaps.md` на шаге 3.5 и `drill/market/signals.md` на шаге 5. Блоки пишет только `career-data-keeper`.

### Шаг 5.5 — сухой прогон парсера (если резюме поедет на hh)
```
python3 scripts/hh_tailor.py parse {company}-{role}
```
Проверить в выводе: заголовок извлечён, «О себе» непустое, навыки собраны, у каждого места работы заполнена должность. Пусто хоть в одном пункте — резюме не соответствует контракту парсера, чинить структуру сейчас, а не в момент заливки, когда документ уже согласован. Требования парсера к структуре перечислены в `reference/resume-format.md` → «Потребители файла».

**Перед первым вызовом внешнего API, меняющим состояние (не-GET), прочитать записи памяти проекта об этой системе и назвать в чате, что из найденного применимо, либо сказать, что записей нет.** Перечень путей в шагах выше работает как whitelist: всё, что вне его, не читается, включая слой памяти, где уже лежит ответ ровно на текущий вопрос. Отдельно про необратимость: если поведение операции удаления не подтверждено документацией или записью памяти, выполнять её сначала на одном элементе и проверять результат, а не на списке.

python3 scripts/export_docx.py <resume.md> <resume.docx>

## Формат ответа: оценка соответствия вакансии

### 0. Проверка покрытия (если черновой score < 90%)
Посчитать score черновиком. Меньше 90% — задать вопросы по недостающим пунктам (см. Жёсткое правило 7 / `gap-discovery.md`), дождаться ответа, только потом выдавать пункты 1-6 ниже с учётом ответа.

### 1. ATS Match Score
Балл 0-100%, краткое объяснение, 10 главных недостающих ключевиков.

### 2. Job Fit Analysis
Сильные стороны / Пробелы / Риски.

### 3. Skills Alignment Matrix
| Требование вакансии | Доказательство в резюме | Статус |
Статусы: Есть / Слабое / Нет.

### 4. Recruiter Perspective
